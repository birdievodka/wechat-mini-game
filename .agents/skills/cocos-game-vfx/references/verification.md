# 验证与交付

## 先证明接通

在实际技能/武器入口释放，确认同一版本的Runtime、Effects和绘制都执行。只调用draw的截图无法证明攻击入口、资源加载或命中回调已经正确接入。

在既有测试框架内补有行为意义的回归，按变更选取：

| 情况 | 观察结果 |
| --- | --- |
| 有效范围内、边界、边界外 | 命中与机制一致，装饰余光不扩大伤害 |
| 尸体、中立物、出生期、无目标 | 按技能规则过滤；空放不伪造接触或命中声 |
| 多目标、重复层与多帧 | 目标上限、每敌次数不随拖尾和重复draw增加 |
| 延迟技能 | 预表现先发生，到真正命中时才扣血 |
| 同帧多次draw | 粒子数、age、任务、充能和随机状态不变化 |
| 暂停/商店/后台 | 表现与任务按项目规则冻结，没有隐藏时间推进 |
| 到期/清场/重开/销毁 | 姿态归零，槽位/节点/资源回收，不残留效果 |
| 池满、屏外、降级路径 | 有限的装饰丢失不改变命中和控制 |

不要写仅搜索某字符串或完全复述绘图实现的测试。行为测试和视觉比较互补，不能互相替代。

## 对着真实画面改

使用相近镜头、人物尺度和阶段对比概念与实现。先看最影响用户感知的内容：

1. 主轮廓是否像该技能，刃面厚度和尖锐边是否在手机尺度成立。
2. 主体与拖尾是否有间隙，峰值是否集中，消散是否及时。
3. 后侧/前侧遮挡、alpha接缝、中心留白、敌方预警可见性。
4. 接触点与真实目标位置是否一致，方向是否跟随实际击退/弹道。
5. 通用命中层、光照或旧材质是否把主题配色污染成其他颜色。
6. 朝向、站立/移动、屏幕边缘和不同英雄的动作叠加是否正常。

静态图无法完整证明旋转/落地/收招节奏，补代表帧、动画或连续体验。横扫0.4秒可取约0.01、0.04、0.08、0.12、0.20、0.28、0.40、0.46秒；其他技能根据真实时长选择，不固定套这组时间。

## 工程布景与用户进度

工程定帧只在确认适合的菜单/非战斗阶段创建，保存需要恢复的运行状态，禁止写战绩或进度，并有异常恢复/watchdog。结束验证原存档和菜单恢复。不要在用户正在玩时插入布景、改生命/金币/计时或重置战斗。

用户要求正常试玩时使用正常输入；测试用高生命敌人和手动推进模拟不能当作真实游玩成绩。修改截图或用概念图伪装实机取证均不可。

`scripts/fixtures/wechat-golden-sweep-review.js`是本项目已有布景案例，执行前先读其menu守卫、restore、watchdog与返回结构，勿假设每个新版本都可直接复用。

## 构建与平台

TypeScript/行为/压力检查按修改范围运行；有新变化或失败再补相关验证，避免反复跑无关测试。需要用户实际体验时执行正式构建，核对运行中的版本、ready和场景，再截图。

微信小游戏通过已安装的wechatide skill/CLI操作；读其门禁、授权、参数与异步规则。不要把小游戏当WXML页面，不使用页面栈工具；CLI成功只说明操作被触发。截图陈旧时比较帧哈希/目标阶段，并检查锁屏或后台状态，不能据旧截图判定新版通过。

新贴图需核对meta、bundle、加载就绪和失败回退；构建后确认主包、分包及总量。如果用户要求二维码，按工具实际成功结果交付；没有要求时不因普通特效改动自动发布、推送或上传。

压力场景用项目实际多武器、多敌、弹幕和危险区，关注实例、内存、draw call/顶点和回收。Node桩的CPU、桌面模拟器的gfx数据都不是手机FPS；未测原设备时明确报告。

## 给用户与后续agent

交付应包含：完成的视觉变化；是否影响机制；可见的当前版本；真实截图/动画及其类型；检查结果；实际设备限制。不要把一次布景的114枚粒子称作全游戏峰值，或把18.51MiB历史包大小当作后续永久预算。

同步项目skill与事实来源。代码更新后，旧概念、旧程序预览和旧验证记录可保留为历史，但不能继续当作最新证据。已有飞书交付要求时写入飞书原生正文/图片，不能只交本地Word；没有授权不擅自往外部服务同步。
